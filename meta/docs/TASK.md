# Тестовое задание для позиции Flutter Senior

Внутреннее название позиции: **Flutter — главный программист**. По уровню ожиданий это **Senior**: разработчик, который проектирует мобильное приложение, готовое к промышленной эксплуатации, обосновывает архитектурные решения и закрывает риски надёжности, данных, безопасности и эксплуатации.

## Контекст

Вы реализуете **CV-Scan Mobile** — мобильный клиент платформы скрининга резюме для HR-специалистов. Приложение работает **offline-first**: пользователь должен иметь возможность просматривать кандидатов, менять их статусы и оставлять заметки даже без сети, а изменения должны **надёжно синхронизироваться** с сервером при восстановлении соединения.

```
[ REST API (контракт зафиксирован) ]  ⇄  [ Движок синхронизации ]  ⇄  [ Локальная БД (источник правды для UI) ]  →  UI
                                              │
                                              └→ очередь изменений + разрешение конфликтов (по версии)
```

Задание проверяет senior-навыки: модульную архитектуру, потребление строгого API-контракта, offline-first и синхронизацию с разрешением конфликтов, нативную интеграцию через platform channels, работу с тяжёлыми данными вне UI-потока (Isolate), безопасность, конфигурацию окружений (flavors), CI/CD и многоуровневое тестирование.

## Технические требования

### Стек
- **Flutter** (актуальная стабильная версия) + **Dart** (sound null-safety)
- **Архитектура**: Clean Architecture (data / domain / presentation) + модульность (**melos**-монорепозиторий или явное разделение пакетов)
- **State management**: BLoC/Cubit **или** Riverpod (обоснуйте выбор)
- **Навигация**: `go_router` (typed routes, redirect/guards, deep links)
- **DI**: `get_it` + `injectable`
- **Сеть**: `dio` (+ `retrofit`), потребление контракта `contract/openapi.yaml`
- **Модели**: `freezed` + `json_serializable`
- **Локальная БД**: `drift` **или** `isar` (источник правды для UI; reactive-запросы)
- **Безопасное хранилище**: `flutter_secure_storage` + нативный слой (Задание 3)
- **Тесты**: `flutter_test`, `bloc_test`, `mocktail`, golden-тесты, `integration_test`

### Что НЕ требуется
- Реальный backend (используется мок/локальный сервер из контракта)
- Серверная часть синхронизации (эмулируйте поведение API по контракту)
- Дизайн-система «с нуля» (достаточно аккуратного Material 3)

## Контракт API

REST API зафиксирован в файле **`contract/openapi.yaml`**.

> **Важно.** Контракт фиксирован — реализовать строго. Не добавлять/переименовывать поля, не менять коды ошибок. Модели и клиент желательно генерировать из контракта (retrofit/openapi-generator) или строго ему соответствовать. Отклонение от контракта приравнивается к ошибке реализации.

Ключевые свойства контракта:
- `GET /candidates` — пагинация (`page`, `size`), фильтр по `verdict`, поиск `q`, сортировка `sort`. Ответ содержит `ETag`/`version` страницы.
- `GET /candidates/{id}` — карточка; в ответе `version` (для оптимистичной блокировки).
- `PATCH /candidates/{id}` — изменение `status`/`note`; **обязателен заголовок `If-Match: <version>`**. При несовпадении версии — `409 VERSION_CONFLICT` с актуальным состоянием в теле.
- `POST /sync` — батч несинхронизированных изменений; ответ — применённые/конфликтные элементы.

Реальный сервер поднимать не нужно: реализуйте `dio`-слой с mock-интерсептором, читающим `mock/*.json`, c искусственной задержкой (300–800 мс), случайными сетевыми ошибками (~10%) и эмуляцией `409` при устаревшей `version`.

## Задания

### Задание 1. Модульная архитектура и контракт

- Организуйте проект как Clean Architecture с модульностью (melos: `app`, `core`, `data`, `features/*`, либо явные пакеты).
- Слой `domain` не зависит от Flutter и от `data` (зависимость направлена внутрь).
- Сгенерируйте/реализуйте модели и API-клиент строго по `contract/openapi.yaml` (freezed-модели, `dio`/`retrofit`).
- Единая модель ошибок (`Failure`) и маппинг сетевых/контрактных ошибок.
- DI через `get_it`+`injectable`, навигация через typed `go_router` (включая deep link на карточку кандидата).

**Критерии:**
- [ ] Чёткое разделение слоёв, корректное направление зависимостей
- [ ] Модели/клиент соответствуют контракту (имена, типы, коды ошибок)
- [ ] Обоснование архитектуры и модульности в README

---

### Задание 2. Offline-first и движок синхронизации

- **Локальная БД — источник правды для UI** (reactive-стримы Drift/Isar). Сеть наполняет БД, UI читает из БД.
- Изменения статуса/заметки доступны офлайн и складываются в **очередь изменений** (outbox) с локальной версией.
- При появлении сети — **фоновая синхронизация** (`POST /sync` или поэлементный `PATCH` с `If-Match`), с повторными попытками и экспоненциальной задержкой.
- **Разрешение конфликтов** по версии: при `409` показать стратегию (server-wins / client-wins / слияние заметок) и довести состояние до консистентного; конфликт не теряется и не зацикливается.
- Индикация состояния: онлайн/офлайн, «есть несинхронизированные изменения», прогресс синхронизации.
- Оптимистичные обновления UI с откатом при неустранимой ошибке.

**Критерии:**
- [ ] UI работает полностью офлайн из локальной БД
- [ ] Очередь изменений переживает перезапуск, не теряет и не дублирует операции (идемпотентность)
- [ ] Корректное разрешение конфликтов по версии (без бесконечных ретраев)
- [ ] Задержка повторов и обработка частичных сбоев синхронизации

---

### Задание 3. Нативная интеграция (platform channels)

Реализуйте функцию с выходом в нативный слой (Android **и/или** iOS, минимум одна платформа полностью):

- **Блокировка приложения по биометрии** при входе/возврате из фона (`local_auth`) **и**
- **Хранение токена/секрета в нативном защищённом хранилище** через собственный `MethodChannel` (Android Keystore / iOS Keychain), а не только через готовый плагин.

Альтернатива (на выбор, с обоснованием): нативный экспорт карточки кандидата в PDF/share через platform channel.

**Критерии:**
- [ ] Реальный `MethodChannel` с нативным кодом (Kotlin/Swift), а не только Dart-плагин
- [ ] Корректная обработка ошибок/отказа пользователя/отсутствия биометрии
- [ ] Секрет не хранится в открытом виде; понимание модели угроз

---

### Задание 4. Производительность и тяжёлые данные

- Список на `mock/candidates-large.json` (1000+ кандидатов) прокручивается плавно (бюджет кадра 16 мс): `ListView.builder`, `const`-виджеты, кэш изображений.
- **Парсинг/агрегация большого JSON выполняется вне UI-потока** (`Isolate`/`compute`), UI не фризится.
- Обоснованная минимизация перерисовок (`buildWhen`/`select`/`context.select`), отсутствие утечек (dispose контроллеров/подписок).
- Контроль производительности: краткое описание, что и как измеряли (DevTools timeline / `flutter run --profile`).

**Критерии:**
- [ ] Нет рывков при прокрутке 1000+ элементов
- [ ] Тяжёлые операции вынесены в Isolate/compute
- [ ] Обоснованная работа с перерисовками и отсутствие утечек

---

### Задание 5. Тестирование (многоуровневое)

- **Unit**: usecase-слой, логика синхронизации и разрешения конфликтов (ключевой фокус ревью).
- **BLoC/Cubit** (`bloc_test`): состояния списка, деталей, синхронизации.
- **Repository**: с фейковыми remote/local источниками (`mocktail`), включая сценарии конфликта и офлайна.
- **Widget + golden**: карточка кандидата и состояния списка (loading/empty/error).
- **integration_test**: E2E-сценарий «офлайн-изменение → синхронизация → консистентность».

**Критерии:**
- [ ] Покрыта логика синхронизации и конфликтов (главное)
- [ ] Есть bloc/repository/widget/golden и хотя бы один E2E
- [ ] Сеть и нативный слой замокированы; проверены граничные случаи

---

### Задание 6. Безопасность и эксплуатационная готовность (доп.)

- **Flavors/окружения** (dev/stage/prod) с разными конфигами (base URL, ключи).
- **Certificate pinning** для `dio` (или обоснованная заглушка с описанием).
- **CI** (GitHub Actions/GitLab CI): `pub get` → codegen → `flutter analyze` → `flutter test` (+ покрытие).
- Хук для наблюдаемости и сбора сбоев (Sentry/Crashlytics — можно за интерфейсом).
- Обфускация релизной сборки (`--obfuscate --split-debug-info`) — описать в README.

**Критерии:**
- [ ] Flavors настроены и работают
- [ ] CI прогоняет анализ и тесты
- [ ] Базовая безопасность (pinning, secure storage, обфускация) учтена

## Ожидаемая структура (пример, melos)

```
packages/
├── core/            # di, network (dio+pinning), router, theme, errors, utils
├── domain/          # entities, repository interfaces, usecases (без Flutter)
├── data/            # freezed-модели по контракту, remote(dio)+local(drift/isar), движок синхронизации, repositories
└── features/
    ├── candidates_list/   # bloc, view, widgets
    └── candidate_detail/  # bloc, view, widgets
app/
├── lib/ (flavors, bootstrap, main_dev/stage/prod)
└── android/ ios/    # нативный код platform channel (Kotlin/Swift)
test/ + integration_test/
.github/workflows/ci.yaml   # или .gitlab-ci.yml
melos.yaml
```

> Допустима не-melos структура с явными слоями, если разделение и направление зависимостей соблюдены. Выбор обоснуйте в README.

## Что оценивается

### Обязательно
- Архитектура: слои, модульность, направление зависимостей, обоснованность решений
- Корректное потребление контракта (модели/ошибки/версионирование)
- Надёжный offline-first: источник правды в БД, очередь, идемпотентность, разрешение конфликтов
- Реальная нативная интеграция через platform channel
- Тесты на ключевую логику (особенно синхронизация/конфликты)

### Будет плюсом
- Golden и E2E тесты, покрытие >70% доменной логики
- Isolate для тяжёлых операций, измеренная производительность
- Flavors, CI, certificate pinning, обфускация
- Аккуратный UX: тёмная тема, анимации, доступность (Semantics)
- ADR/заметки об архитектурных решениях и компромиссах

## Уровневая шкала

| Критерий | Middle | Senior | Strong Senior |
|----------|--------|--------|---------------|
| **Архитектура** | Чистые слои в одном пакете | Модульность, чёткие границы, обоснование | melos, переиспользуемые пакеты, ADR |
| **Offline/Sync** | Кэш + офлайн-чтение | Очередь + конфликты по версии | Идемпотентный движок, слияние, частичные сбои |
| **Нативка** | Готовые плагины | Свой MethodChannel на одной платформе | Обе платформы, модель угроз |
| **Производительность** | builder + const | Isolate, измерения | Бюджет кадра, профилирование, 0 утечек |
| **Тесты** | bloc + repository | + widget/golden | + E2E, >70% домена |
| **Эксплуатация** | — | Flavors или CI | Flavors + CI + pinning + обфускация |
